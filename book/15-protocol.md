# 15. Understand the protocol and wire format deeply

BlindPass's cryptography is an application of a standard protocol, not an invention of a new primitive. A developer still needs to understand what each check proves, because it is easy to compose a secure primitive into an insecure product.

## The mental model: a hidden input and a shared key

Think of a VOPRF as a keyed function evaluated with an extra privacy property. The issuer has secret key `k`; the client has input `x`. The client sends a blinded representation of `x`, the issuer evaluates it with `k` and supplies a proof, and the client unblinds to obtain a result corresponding to `F_k(x)`. The issuer does not learn `x` from the correctly blinded request. Later, the privately verifiable token can be checked by a verifier with the issuer secret. The actual math, group operations, proof transcripts, and serialization are delegated to the pinned libraries.

This model has three important qualifications. First, blinding hides the token input from the issuer, not the network endpoint or purchase capability used to request issuance. Second, the proof checks key consistency, not payment status or global policy consistency. Third, privately verifiable means the verifier needs private key material; this affects service separation and blast radius. An independently operated verifier would require a different trust arrangement or token type.

## Walk through the repository implementation

[`challengeFor`](../packages/privacy-pass/src/index.ts) hashes canonical application context containing a domain string, token class, epoch, and expiry. It constructs a standard `TokenChallenge` with issuer and origin scope. The library then derives the challenge digest used in the token input. The client creates ten `privateVerif.Client` instances and asks each to create a token request against the shared public key. Each instance retains its own hidden state until `finalize`.

The issuer receives serialized request bytes and uses `privateVerif.Issuer.issue`. The wrapper rejects a request of the wrong length or with a mismatched truncated key ID before asking the library to evaluate it. The response is an evaluated element and proof. The client checks response count and length and calls `finalize`, which verifies the proof and constructs the token. The server later deserializes a canonical token and calls the library's verifier. The application additionally checks full key ID, time window, class, and challenge digest.

The wrapper currently expects 52-byte request, 145-byte response, and 146-byte token encodings for its selected token type. Treat these as invariants of this implementation and its pinned protocol version, not universal lengths for every Privacy Pass token type. The JSON array of ten requests is an application transport envelope. A different conforming issuer will not automatically understand that envelope.

## Why canonical bytes matter twice

The signing layer canonicalizes JSON before Ed25519 signing. The credential layer canonicalizes serialized token bytes before hashing them for replay detection. These are distinct rules solving distinct problems. A valid signature over one JSON interpretation should not be accepted as a different document because of key ordering or ambiguous representations. A valid token should not acquire multiple spent identities because a deserializer ignores trailing bytes or accepts alternate base64 spellings.

The header parser requires a single `PrivateToken token="..."` value with canonical padded base64url bytes. It checks the encoded value round-trips and has the expected length. The spent hash includes a domain prefix, then the canonical token bytes. If you change the parser or encoder, add a test showing one logical token cannot be redeemed under two byte encodings. This is a security regression test, not formatting trivia.

## The shared challenge is an anonymity constraint

Every buyer in a UTC month shares token class `search-v1`, key, issuer, origin, challenge context, and expiry. The only per-token secret input is fresh randomness generated by the client. If the server inserted the invoice ID into challenge context, it could recognize the invoice when that token appears at redemption. A per-invoice key or expiry would have the same partitioning effect. A fixed batch size and denomination reduce additional clues, though they cannot erase timing and network metadata.

The client validates the manifest _before_ creating requests and validates the returned configuration _again_ before finalization. The latter prevents a server from changing context between request and response. However, a signed manifest can still be malicious if the merchant selects a different valid manifest for every first-time client. The cryptographic proof does not address equivocation; independent publication or transparency is a separate system requirement.

## Key lifecycle changes protocol behavior

The active key is registered in the database under the current UTC month. Issuance stops at the next month boundary; verification accepts that month's tokens until the common seven-day grace expiry. New invoices near the boundary receive a deadline capped by issuance end. Previous keys must remain available to the verifier during grace. The current service loads epoch keys at startup, so crossing the boundary requires coordinated rotation and restart. If one API node runs a different key, clients may receive inconsistent manifests or valid credits may fail verification on some nodes. Clock synchronization is part of correctness.

## A protocol exercise

For each statement below, identify the responsible control: (a) “the request was paid,” (b) “the issuer used the advertised VOPRF key,” (c) “the client received the same monthly policy as before,” (d) “this token has not been spent,” and (e) “the merchant did not give two first-time clients different monthly keys.” The answers are respectively payment authorization, library proof verification, client manifest pin/cache, database uniqueness, and an _unimplemented_ independent consistency mechanism. If you answer “cryptography” for all five, the composition is not yet understood.
